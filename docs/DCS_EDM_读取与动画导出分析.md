# DCS EDM 读取与动画导出分析

本次实现的目标是直接读取 EDM 并输出可在通用软件中播放的模型动画。研究采用三种证据：社区格式资料、真实 EDM 文件的逐字节解析，以及本机 DCS 动画函数和着色器的只读核对。以下“已验证”均指文中列出的文件和 DCS 构建，不等于覆盖全部历史版本或第三方变体。

0.3 更新：已加入涂装目录发现、动态 Lua 求值、RoughMet PBR 和 NumberNode 编号预览/导出。选择涂装时，文中其他参数归零的规则改为优先保留其 `custom_args` 默认值及用户设置的编号。详见 [涂装支持说明](涂装支持说明.md)。

## 1. 文件读取流程

```text
文件签名 EDM + uint16 版本
    ↓
v10 全局字符串表（v8 无此表）
    ↓
indexA / indexB 类型计数索引
    ↓
RootNode：边界信息、材质、顶点格式、纹理引用、属性
    ↓
场景节点数组：静态变换、骨骼、参数动画、可见性、LOD
    ↓
父索引数组：恢复完整场景层级
    ↓
Render Items：渲染网格、蒙皮、编号、灯光、碰撞、连接点
    ↓
EOF / 范围 / 索引 / 父链循环校验
    ↓
独立的场景表示 → 参数求值 → GPU 预览或 glTF 输出
```

整数与浮点使用小端序。类型名决定紧接着读取哪个结构体；数组通常有长度前缀。v10 类型和属性字符串通过全局表引用，但节点名称仍使用长度前缀字符串。矩阵为 16 个 double；四元数文件顺序为 xyzw。社区规范提供了这部分基础结构：[EDM Specification](https://ndevenish.github.io/Blender_ioEDM/EDM_Specification.html)。

本实现以 MIT 授权的独立 Python 解析包为起点，去除了运行时对 Blender 的依赖，并修正真实文件中发现的问题。原项目：[DCS-EDM-Blender-Importer](https://github.com/devozdemirhasancan/DCS-EDM-Blender-Importer)。

`indexA/indexB` 在部分当前文件中为空，不能把它们作为唯一完整性依据。软件要求读取到准确 EOF，校验顶点步长、三角索引、材质索引、骨骼引用、父链及关键帧。未知布局立即报错，不在顶点字节流里搜到类似类型名后继续猜读。

## 2. 本次确认的几何读取问题

### NumberNode 包含完整网格

在 F-16C 和 F/A-18C 实测中，布局为完整 RenderNode，再跟随一个计数及 `count × 16` 字节的控制记录。控制记录按 `int32 / float32 / uint32 / float32` 读取并保留。

把 NumberNode 当成普通整数，会使游标错位；用类型搜索恢复会丢失机身编号网格，甚至误把属性当成渲染节点。修正后 F/A-18C LOD2 的 15 个 NumberNode 全部读取，文件没有剩余字节。编号贴图的实时切换仍是 DCS 专用材质行为，当前只保留控制元数据，不伪装成已转换的动画。

### 多父节点不能只按 indexStart 切分

Su-25T 的该字段实际上呈现累积结束索引；F/A-18C 的部分多父表全部填 0。当前着色器使用 `POSITION.w` 指定每个顶点所属的变换槽。

软件优先按每个三角面顶点的父槽分组，并校验三个顶点一致；缺少该通道时才处理已识别的范围布局。这避免了多个部件共用材质时被错误地绑定到最后一个父节点。

### 蒙皮骨骼索引是打包字节

不能把 `POSITION.w` 当成一个数值浮点骨骼编号。其原始 32 位字节包含四个 uint8 索引。使用 NumPy 从原始字节直接读取，避免 Python 浮点转换改变特殊位模式。

本机 `Bazar/shaders/model/functions/vt_utils.hlsl` 确认：四个打包索引均需要 **加 1**；权重在通道 21。另有一个隐含权重 `max(0, 1 - 四权重之和)` 作用于骨骼表第 0 项。需要第五个影响时，输出标准 `JOINTS_1 / WEIGHTS_1`，不丢弃、不猜测无权重顶点。

## 3. 动画实际如何计算

EDM 的“关键帧横坐标”是 DCS argument 值，不是视频时间。起落架、座舱盖等动作一般由不同参数控制，同一参数可以影响很多节点，也可能出现负值或大于 1 的范围。

使用列向量写出本机 `UniModelDesc.dll` 的实际计算结果：

```text
Local = M · T(p + Σ positionTrack)
          · Q1 · Rn · … · R1
          · inverse(Q2) · Sbase · Q2
          · inverse(Qsn) · Sn · Qsn
          · …
          · inverse(Qs1) · S1 · Qs1

World(child) = World(parent) · Local(child)
```

- 位置轨道按参数线性插值后相加。
- 旋转轨道使用最短弧四元数插值；多个旋转轨道的乘积顺序必须与 DCS 一致。
- **Q2 是缩放轴方向**，不是直接接在末尾的普通姿态旋转。
- Scale 的两组关键帧分别是缩放方向四元数（四分量）与缩放向量（三分量）；四分量不能作为 xyz 缩放读取。
- 带方向的非均匀缩放可能产生剪切。把整条链粗暴分解成一组 TRS 会丢失信息。

软件把各项拆成明确的 glTF 父子节点。静态仿射矩阵通过 SVD 分成可表示的 TRS 因子，旋转、平移和缩放轨道分别绑定对应节点，因此不用依赖逐帧近似烘焙来掩盖变换错误。

可见性是单独的渲染条件：同一个参数的多个区间是 OR，不同参数之间是 AND；区间为 **起点包含、终点不包含**。它不应修改原骨骼计算。对刚体网格增加末端可见性控制；对蒙皮使用受相同可见性控制的骨骼副本，保证隐藏时整个部件消失。

## 4. 原生核对方法与结果

研究工具在独立 Python 进程内调用 DCS DLL 的纯数学函数。不启动、不附加、不修改游戏进程。产品程序不加载这些 DLL，运行时完全独立。

已核对构建的 `UniModelDesc.dll` SHA-256：

```text
f1f03eacda2e0bf1aaa8bf2eb7167dcc0bb557deccf9d0328c5e2d2b6e9d4d73
```

关键函数为 `model::ArgAnimationNode::animate`，本机构建 RVA `0x54fc0`；可见性为 `model::ArgVisibilityNode::isVisible`，RVA `0x59120`。研究工具带哈希检查，禁止把这套内部对象偏移直接套用到其他构建。

对每个动画节点，使用参数 `-1、0、0.137、0.5、0.873、1` 比较软件重建的完整本地矩阵与 DCS 返回矩阵：

| 模型 | 比较次数 | 最大矩阵元素绝对误差 |
|---|---:|---:|
| F/A-18C LOD2 | 2,958 | 1.4225e-6 |
| F-16C BL50 | 1,788 | 1.1281e-6 |
| Su-25T | 864 | 8.6600e-6 |

这些是实际测量，不只是公式自测。误差包括 EDM 原始四元数的精度、DCS 参数 float 精度及归一化差异。该检查验证动画节点变换；不声称已对 DCS 所有材质和最终像素渲染做一致性测试。

证据文件：`validation/native_animation_results.json`；可复现工具：`tools/validate_native.py`、`tools/native_oracle.py`。原生反汇编和结构探测脚本仅用于研究。

## 5. 导出为通用动画

采用 glTF 2.0 / GLB，标准参见 [Khronos glTF specification](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc)。

每个参数输出一个 `Argument NNN` 动画片段：

```text
time = (argument - minimum) / (maximum - minimum) × duration
```

原始范围、参数编号和片段时长写入 animation extras。位移和缩放为 LINEAR，旋转为标准四元数 LINEAR/Slerp，可见性为 STEP。对同一片段，其他参数回到 0，防止切换片段时沿用前一段残留状态。

骨骼的逆绑定矩阵、最多八个权重槽、法线、多 UV、连接点、材质名和参数属性得到保留。GLB 内嵌二进制和可解析的漫反射贴图；glTF 选项使用 data URI，仍可作为单文件传递。

输出先在内存中形成完整数据，再原子写入目标文件；同时生成同名 `.report.json`。这份报告包含网格/动画数量、缺失贴图和转换限制。

## 6. 通用格式与回读验证

- F/A-18C 主模型：**490,186 个三角面、733 个网格、153 个参数动画**，全部动画导出通过 Khronos glTF Validator，0 error / 0 warning。
- F/A-18C LOD2：11 段动画回读，在每段三个中间位置对完整场景求值，总计比较 **700,755** 个节点矩阵，最大误差 **2.534e-6**。
- F/A-18C LOD2 带贴图版本、F-16C 测试动画版本均通过 Khronos 校验，0 error / 0 warning。未参与当前 PBR 的额外 UV 会产生 informational 的 UNUSED_OBJECT，不是格式错误。
- 软件界面通过自身窗口截图验证，OpenGL renderer 为 **NVIDIA GeForce RTX 5080**。
- 独立 EXE 同样通过真实 EDM 读取、GPU 预览和动画导出验证，见 `validation/frozen_smoke.json`。打包使用受控 DLL 搜索路径，避免构建机器上 Poppler 的 ICU DLL 与 Qt 使用的 Windows ICU API 冲突。
- Blender 5.2.1 独立导入带贴图 GLB 成功，得到 `Argument 000/003/005/038` 四个动作。对同一批顶点在两帧求值，最大位移 2.152 米，确认实际导入的动作可以驱动几何。导入耗时约 153 秒。
- `tests/test_conversion.py` 有 8 项回归测试，覆盖易损坏的文件和动画语义。

回读工具：`tools/validate_roundtrip.py`。Khronos 报告：`validation/*.validation.json`。Blender 独立导入检查工具：`tools/blender_import_check.py`，运行结果另存 JSON。

## 7. 当前边界

### 0.3.4 F-100D 的聚光灯布局

F-100D 使用带 `__VERSION__ = 2` 属性的 `FakeSpotLightsNode`。每盏灯记录为 77 字节，比缺省/版本 1 的 65 字节多三个 float32；结合本机材质 `fake_spot_lights2_wdir` 与向量值，推断这三个值为方向。FA-18C LOD2 的版本 1 记录仍为 65 字节，已对照验证。解析器按显式版本选择记录长度，未知版本报错。

F-100D 末尾的 5 个聚光灯节点包含 6 条灯记录，其中一个节点有 2 条，扩展按每条记录读取。读取后严格到达文件末尾 `166742841`，没有跳过未知尾部或按特征扫描重定位。场景和几何数据正常保留；DCS 专用假灯光没有转成普通网格，仍会给出转换限制提示。

验证覆盖 EDM v8/v10 中连续排列的旧布局、版本 1、版本 2 灯节点及其后的真实几何记录。真实 F-100D 的 8 个参数片段（0、3、5、9、10、11、12、38）导出校验 0 error / 0 warning，回读比较 1,689,432 个节点矩阵，最大误差 `1.44e-6`。

### 0.3.2 可见性节点的版本 1 布局

本机 `Bazar/World/Shapes/C-130_lod0.edm` 的部分 `ArgVisibilityNode` 在属性集中保存 `__VERSION__ = 1`，在所有可见性参数区间之后附加一个 16 个 float32 的矩阵（64 字节）。旧版未消费这段数据，导致从下一场景节点开始把矩阵的 `1.0f` 位模式 `1065353216` 当成字符串表索引。

解析器现在依据节点的显式属性读取扩展矩阵，原布局（属性缺省或为 0）仍不读取扩展；未知版本直接报错。对 C-130 从文件起点严格顺序解析到 EOF，共 136 个节点、26 个合批 RenderNode，展开后 184 个网格；未通过扫描字节特征跳过内容。实测扩展矩阵均为单位矩阵，保存在导出节点元数据中，不改变已有显隐区间。非单位扩展矩阵的运行时语义尚未验证，当前明确拒绝转换，以免错误摆放模型。

24 项测试覆盖原布局、版本 1 布局及其 GLB 显隐动画边界。真实 C-130 的 41 段参数动画通过 Khronos 校验，选定片段回读最大矩阵误差为 `8.57e-8`，RTX 5080 预览成功。此文件使用的是传统 specular 贴图，不能把它直接当作 RoughMet；实测 14 个漫反射材质、0 个 RoughMet 材质。

### 0.3.1 镜像面与近距离显示修正

F-14B 右翼部分刚体部件在 EDM 内使用负行列式变换，局部三角面顺序也已经反向。旧版仅按节点行列式调整正面规则，导致这些部件的外表面被当成背面剔除。实际检查右侧襟翼等网格，三角面几何法线与顶点法线方向相反；保持背面剔除开启并统一局部面顺序后，缺失的蒙皮恢复。

导入阶段按三角面面积加权比较几何法线和顶点法线：可靠证据覆盖超过一半面积，且其中超过 95% 反向时，整体交换每个三角面的两个索引。混合、歧义或退化表面保持原样。实际 F-14B 有 91 个网格得到修正；顶点、UV、骨骼权重与动画变换不变，预览和导出共同使用修正后的索引。负缩放节点继续按 [glTF 正面判定规则](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#meshes) 处理。

旧相机在近距离把近裁剪面降到 0.001 米，24 位深度缓冲难以区分临近表面。现在近裁剪面随观察距离调整：实测距离 12 米时从 0.001 米提高到 0.06 米，远裁剪面从 100 米调整到 81.74 米。保留近距离观察并减少翼缝锯齿；[OpenGL 深度精度说明](https://wikis.khronos.org/opengl/Depth_Buffer_Precision) 解释了近裁剪面对精度的影响。

`tools/depth_smoke.py` 在同一真实 GPU 视口、同一相机下还原旧行为并保存修复前后截图；`tests/test_surface_orientation.py` 检查镜像网格的实际 GLB 索引与近距离精度。此修正不等于已经复刻全部 DCS 材质效果。

已完成几何与参数驱动的变换/蒙皮/可见性动画转换；0.3 增加 RoughMet 的标准 ORM 通道映射与 NumberNode 图集编号。编号片段使用 0.1 参数步长的标准 glTF STEP 节点。以下内容不属于本版的完全等价转换范围：DCS 专用 shader/环境反射、法线贴图、其他材质参数动画、半透明编号与底色的混合、损伤遮罩、特殊假灯光、billboard 跟随相机、游戏运行时物理/粒子效果。内部 LOD 保留层级元数据，未按相机距离自动切换。

因此“能正确导出飞机动作”与“完全复刻 DCS 渲染”是不同的验收项。本版对前者提供原生函数和文件回读证据；对后者在界面及报告中明确给出限制。
